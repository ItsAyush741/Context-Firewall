computer-use	sessions	—	a	well-documented	failure	mode	has	emerged:	
context	rot
,	the	measurable	degradation	of	model
output	quality	as	the	context	window	fills	with	accumulated,	increasingly	irrelevant	tokens.	This	is	not	context	overflow	(hitting
the	token	limit);	it	happens	well	before	the	limit,	simply	because	the	model's	attention	gets	diluted	across	noise.
I	propose	to	build	the	
Context	Rot	Firewall
:	a	middleware	layer	that	sits	between	an	autonomous	agent	and	its	context	window,
continuously	scoring	every	message	and	tool	output	for	relevance	to	the	agent's	current	sub-goal,	and	actively	compressing,
archiving,	or	evicting	low-relevance	content	before	it	degrades	reasoning	—	instead	of	the	naive	"keep	everything"	or	"truncate
oldest-first"	strategies	most	agent	frameworks	use	today.
Core	deliverable:
	a	pluggable	Python	library	+	dashboard	that	wraps	around	any	agent	loop,	and	a	benchmark
demonstrating	that	task	success	rate	holds	up	over	long	sessions	with	the	firewall	active,	versus	measurably	degrading
without	it.
The	project	is	engineering-heavy	and	ML-light	—	no	model	training	or	fine-tuning	is	required,	which	keeps	it	feasible	within	a
student	budget	and	timeline.	It	sits	inside	an	active,	fast-moving	subfield	of	AI	(context	engineering	for	agents)	with	real,	citable
industry	research	behind	the	problem	statement,	and	I	believe	there	is	a	genuine	gap	in	the	existing	tooling	landscape,	detailed	in
Section	5.
2.	Problem	Statement
2.1	What	context	rot	actually	is
Context	rot	is	the	term	used	across	recent	industry	and	academic	work	for	a	specific,	measurable	phenomenon:	as	more	tokens
are	added	to	an	LLM's	input,	output	quality	decreases	—	even	when	the	model	is	nowhere	near	its	advertised	context	limit.
Chroma's	widely-cited	2025	research	tested	18	frontier	models	and	found	the	effect	present	in	every	single	one,	not	just	some.
For	 agentic	 systems	 specifically,	 this	 is	 compounding	 rather	 than	 incidental.	 Every	 tool	 call,	 file	 read,	 search	 result,	 and
intermediate	reasoning	step	adds	tokens	to	the	running	context.	None	of	it	gets	removed	by	default	in	most	agent	frameworks,	so
the	signal-to-noise	ratio	inside	the	context	steadily	degrades	across	a	session,	and	the	model's	ability	to	attend	to	what	actually
matters	—	the	current	sub-goal	—	drops	accordingly.	Practitioner	write-ups	from	2026	report	that	agent	coherence	visibly	declines
once	sessions	pass	roughly	20–30	turns,	well	before	any	token	ceiling	is	hit.
The	underlying	mechanism	is	architectural,	not	a	model	bug:	attention	weights	are	normalized	(softmax)	across	the	entire
context,	so	as	context	length	grows,	each	individual	token	—	including	early,	important	instructions	—	receives	a	proportionally
smaller	share	of	attention.	Separately,	models	exhibit	a	documented	"lost-in-the-middle"	positional	bias,	performing	best	when
relevant	information	sits	at	the	very	start	or	end	of	the	context	and	worse	when	it	is	buried	in	the	middle.
2.2	Why	this	matters	right	now
Timing:
	2026	is	the	year	long-horizon	agents	(coding	agents,	browser/computer-use	agents,	multi-step	research	agents)	are
moving	from	demo	to	production,	which	is	exactly	when	this	failure	mode	becomes	operationally	important	rather	than
academic.
No	standard	fix:
	most	agent	frameworks	still	handle	this	with	blunt	strategies	—	fixed-size	sliding	windows,	oldest-first
truncation,	or	leaving	it	entirely	to	the	base	model	—	rather	than	an	active,	relevance-aware	management	layer.
Safety	angle:
	degraded	attention	doesn't	only	blunt	task	performance.	Recent	work	has	shown	that	as	padding/context
length	 grows,	 safety-relevant	 instructions	 defined	 early	 in	 a	 session	 can	 also	 get	 diluted	 —	 a	 secondary	 but	 relevant
motivation,	even	though	this	project's	core	contribution	is	systems	engineering,	not	classification.
3.	Proposed	Solution
3.1	Concept
I	propose	a	middleware	layer	—	not	a	new	agent	framework	—	that	intercepts	the	context	an	agent	is	about	to	send	to	the	model
on	every	turn,	and	actively	manages	what	stays,	what	gets	compressed,	and	what	gets	moved	to	retrievable	cold	storage.	The
---PAGE---
guiding	principle:	
relevance	to	the	current	sub-goal
,	not	recency	and	not	raw	token	budget,	determines	what	the	model	actually
sees.
3.2	System	architecture
Component
Function
Context
Interceptor
Wraps	the	agent's	LLM	call;	captures	the	full	running	message/tool-output	history	before	each	generation	step.
Relevance
Scorer
Scores	each	chunk	in	the	running	context	against	the	current	sub-goal.	Two-tier:	(1)	cheap	embedding-similarity	pass	for
bulk	scoring,	(2)	LLM-judged	relevance	pass	only	for	borderline	chunks,	to	keep	cost	down.
Compression
Engine
Chunks	below	the	relevance	threshold	get	summarized	into	a	short	note	rather	than	deleted	outright	—	preserving	gist
while	freeing	tokens.
Cold	Storage	/
Retrieval
Full	original	chunks	are	archived	(vector	store)	and	remain	retrievable	if	a	later	sub-goal	needs	them	back	—	analogous
to	OS	memory	paging.
Context
Health
Dashboard
Live	view	of	token	budget	usage,	relevance-score	distribution,	eviction/compression	events,	and	(in	eval	mode)	task-
success-rate	over	session	length.
3.3	How	it	differs	from	"just	summarizing	everything"
Naive	summarization-on-overflow	(what	most	agent	harnesses	do	today,	including	basic	
/compact
-style	commands)	compresses
everything	 indiscriminately	 once	 a	 token	 ceiling	 is	 approached.	 The	 Context	 Rot	 Firewall	 instead	 scores	 continuously	 and
selectively,	so	highly	relevant	recent	tool	output	is	kept	verbatim	while	stale,	irrelevant	material	is	compressed	early	—	before	it
ever	contributes	to	attention	dilution,	and	independent	of	whether	the	token	ceiling	is	close.

A	benchmark	does	not	need	to	be	built	from	scratch.	The	evaluation	methodology	can	adapt	Chroma's	Context	Rot	approach	(an
extended	 Needle-in-a-Haystack	 test	 with	 semantic	 matching,	 plus	 a	 conversational	 QA	 evaluation	 called	 LongMemEval)	 to
measure	task	accuracy	at	increasing	context	lengths,	with	and	without	the	firewall	active.	A	second,	cheaper	evaluation	track
uses	self-authored	multi-step	coding	or	research	tasks	run	to	40–60	turns,	tracking	whether	the	agent	stays	on-goal.
4.4	Cost	feasibility
Entirely	buildable	at	zero	monetary	cost:	open-weight	models	on	free-tier	compute,	free/open	vector	databases,	and	API-based
evaluation	limited	to	a	small	number	of	calls	against	a	free-tier	or	low-cost	hosted	model	for	the	final	comparison	runs.	No	paid
dataset,	no	paid	compute	is	required	for	a	complete,	demoable	Sem	1	+	Sem	2	deliverable.

6.	Why	I	Believe	This	Is	a	Strong	Final-Year	Project
Not	a	research	replication.
	This	is	not	a	reproduction	of	a	known	result;	it	is	a	scoped	tool	occupying	real,	currently-thin
space	between	two	categories	of	existing	work	(persistent	memory	frameworks	vs.	reactive	compaction	commands).
Demoable,	not	abstract.
	The	core	result	is	a	graph:	task	success	rate	over	session	length,	with	vs.	without	the	firewall.	That
is	a	clean,	convincing,	live	demo	—	not	a	paper	full	of	numbers	nobody	outside	the	field	can	evaluate.
Infrastructure	framing.
	"I	built	a	pluggable	middleware	layer	that	any	agent	framework	can	wrap"	is	a	stronger	interview
sentence	than	"I	built	a	classifier,"	because	it	signals	systems	thinking,	not	just	an	ML	exercise.
Low-risk	build	profile.
	No	training,	no	large	datasets,	no	paid	infrastructure	—	the	project's	risk	is	entirely	in	engineering
execution,	which	is	controllable,	not	in	whether	an	experimental	technique	works	at	all.
